# 實體水域測試協議：閘門偵測特性量測

> 建立日期：2026-08-31
> 目的：取得**真實場地**的「偵測率 vs 距離 vs 深度」曲線，並回答
> 「閘門橫桿露出水面時能否穩定辨識」這個目前無法在模擬中回答的問題。
> 前置閱讀：[`GATE_DETECTION_RANGE_FINDINGS.md`](GATE_DETECTION_RANGE_FINDINGS.md)（模擬版的同一組量測）

---

## 0. 為什麼需要這份文件

截至建立日，`bags/` 裡 37 個 bag、3.8 GB，抽查 rosout 全部含
`Creating ROS->GZ Bridge` —— **全部是 Gazebo 模擬**。其中只有一個
（`orca_20260830_025831`，88 秒）錄到相機影像。

**團隊目前持有的真實水下影像數量為零。**

而模擬無法回答橫桿問題，原因在物理層不在參數層：真實水面會產生**鏡面倒影**
（橫桿在水面下看起來是兩根）、**Snell 窗**（斜上方視野邊緣是全反射的鏡面）、
**碎波造成的逐幀扭曲**。相機在水下 0.2 m 前視時，水面就落在畫面上緣，
這三種效應正好全部疊在橫桿的位置上。Gazebo 的水面是單一平面 shader，
三者一個都沒有模擬。

因此第一次下水的目標順序是：**資料 > 標定 > 任務**。
不要把寶貴的下水時間花在 debug 行為樹。

## 1. 與模擬量測最關鍵的差異：距離真值

模擬有 `ign model -p` 提供真值位姿；**真實水域沒有**。
沒有距離真值，錄回來的影片就畫不出偵測率 vs 距離曲線，整趟等於白費。

這是最容易到現場才發現漏掉的一環，所以放在最前面。

### 1.1 採用「定點站樁法」，不要沿用模擬的「開過去」

模擬版 §3.1 用的是「手動推力開過去 + 事後對時間軸內插」。
**在真實水域不要這樣做** —— 因為沒有連續的位置真值可以內插。

改用離散定點：

1. 把載具固定在**已知距離**的位置
2. 在該位置**靜止錄 20–30 秒**（約 150–250 幀，足夠算出可信的偵測率）
3. 換下一個距離，重複

距離真值變成離散但精確，而且**完全不需要時間軸對齊** ——
事後只要按時間段切割 bag 即可。

### 1.2 定位方式（現場擇一，事前就要決定並準備）

| 方式 | 適用 | 需要準備 |
|---|---|---|
| **人員涉水扶持**（推薦） | 淺水區、載具輕 | 無。隊員站在水中扶住載具，照池邊標記對位 |
| **繩索標定** | 深水區 | 一條每 0.5 m 打結的繩，一端固定在門，一端牽到載具 |
| **池底刻度** | 能見度好 | 事前在池底貼防水標記（每 1 m） |

⚠ **不要用 `depth_hold` 讓載具自己站樁。** 模擬版 §5.3 已經記錄過：
decision node 自己也在發布 `desired_depth`，兩個發布者會互搶，
實際深度會偏離設定值 0.4 m 以上。真實水域同樣的架構同樣會發生。
**站樁期間讓系統維持 `manual` 模式、推進器不出力，由人或繩固定。**

### 1.3 利用場地本身當尺規

比賽泳池的水道線與 T 字標記間距是標準化的（50 m 池：T 字標記距池壁 5 m，
水道線全長貫通）。**事前查好該場地的實際規格並記在下表**，
現場就能直接讀距離，不必另外拉尺：

| 場地特徵 | 實測間距 | 現場確認 ☐ |
|---|---|---|
| 水道線寬度 | ______ m | ☐ |
| T 字標記距池壁 | ______ m | ☐ |
| 水道寬（線到線） | ______ m | ☐ |
| 池底磁磚邊長 | ______ m | ☐ |

## 2. 下水前（在陸上完成，不要留到現場）

### 2.1 錄影流程要先跑順

37 個 bag 只有 1 個錄到相機，代表這條路徑還不熟。**在陸上驗一次完整流程**：

```bash
make launch RECORD_IMAGES=true
```

`RECORD_IMAGES` **兩個堆疊都要收到** —— autonomy 負責把四路相機轉成壓縮影像
（壓縮外掛只有那個容器有），control 負責錄。只開一邊會錄到一組空 topic。

驗收條件（全部要打勾才算通過）：

- ☐ `/orca/record/front/compressed` 有訊息且畫面正常
- ☐ `/orca/record/detections/compressed` 有訊息（疊圖有框）
- ☐ `/orca/perception_array` 有訊息
- ☐ bag 檔案大小隨時間成長
- ☐ 停止錄製後 bag 能正常讀取（不是損毀的 `.mcap.active`）

### 2.2 儲存空間

模擬全鏈路實測約 **1.3 MB/s ＝ 80 MB/min**。真實場地四路相機加上更高的畫面
複雜度（JPEG 壓不掉的細節多），**抓 150 MB/min 比較保險**。

```bash
make status   # 會印出 ORCA_BAG_DIR 的剩餘空間
```

⚠ `ros2 bag record` **沒有總容量上限**，`min_free_space_gb` 也只在啟動時檢查
一次，所以錄下去會一路寫到磁碟滿為止。

| 項目 | 數值 |
|---|---|
| 預計錄影總時數 | ______ 分鐘 |
| 需要空間（× 150 MB/min） | ______ GB |
| 現場可用空間 | ______ GB |
| 備援（外接碟／換卡） | ☐ 已準備 |

### 2.3 分段標記機制

站樁法需要知道「哪一段時間對應哪一個距離」。**不要靠事後看影片猜。**
每換一個設定，在錄製中打一個標記：

```bash
ros2 topic pub --once /orca/test/marker std_msgs/msg/String "{data: 'd=5.0 depth=0.2 sun=direct angle=0'}"
```

- 事前把 `/orca/test/marker` 加進 `SAUVC-RPI/rpi_ros2_ws/src/orca_bringup/config/record_topics.yaml`，否則不會被錄下來
- 備援方案（萬一 topic 沒錄到）：換設定時**用手在鏡頭前遮 2 秒**，事後從影片就能切段

### 2.4 現場帶什麼

- ☐ 防水記錄板 + 油性筆（現場紙本填第 3 節的表）
- ☐ 捲尺（就算打算用場地標記，也要能驗證一次）
- ☐ 打結繩（每 0.5 m 一個結，長度 ≥ 12 m）
- ☐ 筆電 + 充電 + 網路熱點
- ☐ 外接硬碟
- ☐ 一台手機／相機架在池邊，全程側錄整個測試過程（事後回查現場狀況用，非常有用）

## 3. 現場測試矩陣

**照著打勾，不要靠臨場判斷決定測什麼。**
每一格站樁 20–30 秒。粗體是重點格（模擬中的死區），沒時間時優先保這些。

### 3.1 主矩陣：距離 × 深度（正對閘門，光照記錄當下條件）

| 距門 | 深度 0.2 m | 深度 0.5 m | 深度 0.8 m |
|---|---|---|---|
| 9.0 m | ☐ | ☐ | ☐ |
| 7.0 m | ☐ | ☐ | ☐ |
| 5.5 m | ☐ | ☐ | ☐ |
| **4.5 m** | ☐ | ☐ | ☐ |
| **3.5 m** | ☐ | ☐ | ☐ |
| **2.5 m** | ☐ | ☐ | ☐ |
| **1.5 m** | ☐ | ☐ | ☐ |

> 深度 0.2 m 是目前 `trees.xml` 的設定（`SetDepth depth="0.2"`）。
> 0.5 / 0.8 m 是為了測「潛到反光層底下」的假說 —— 立柱從水面延伸到 -1.6 m，
> 0.8 m 深仍安全通過門，但相機會避開水面反光帶。
> **若時間只夠測一種深度，測 0.2 和 0.8 的對比，中間那格可以捨。**

### 3.2 次要矩陣：角度（固定深度 0.2 m，距離 5.5 m）

| 相對閘門法線 | 打勾 |
|---|---|

| 15° | ☐ |
| 30° | ☐ |
| 45° | ☐ |

用途：判斷 `ApproachTarget` 的 `error_x > 60` 先轉再走的門檻設得合不合理。

### 3.3 光照（同一組距離重跑，優先度最低但價值高）

| 條件 | 時間 | 打勾 |
|---|---|---|
| 正午直射 | ____ | ☐ |
| 陰天／雲遮 | ____ | ☐ |

> 貼出的場地照片是強烈直射陽光。逆光那格若能取得，價值最高 ——

## 4. 獨立測項（不屬於矩陣，但必做）

### 4.1 Yaw 漂移測試（5 分鐘，優先度最高）

**這個測試不做，所有導航設計都建在沙上。** 泳池邊全是鋼筋、看台、電子設備，
若 IMU 航向融合了磁力計，讀值可能被拉偏。

程序：

1. 載具靜置，記錄 `/orca_auv/state/orientation` 的 yaw 初值
2. 手動讓載具原地順時針轉 3 圈，回到目視原朝向
3. 記錄 yaw 終值
4. 逆時針重複一次
5. 靜置 5 分鐘，看 yaw 有沒有慢速漂移

| 項目 | 允收 | 實測 |
|---|---|---|
| 轉 3 圈後回位誤差 | < 5° | ______ |
| 靜置 5 分鐘漂移 | < 2° | ______ |

**若不合格**：`heading memory` 與 `TurnToYaw degrees="180"` 都不可信，
導航策略必須改用純視覺回授，整個規劃要重來。所以這格務必早做，
不要排在測試日的最後。

### 4.2 推力→速度標定

模擬裡對 `surge=25` 的速度估計是 0.27–0.5 m/s，**2 倍的不確定性**，
而所有 `BlindForward` 都是用時間當參數。真實水的阻力、電池電壓、配重都不同,
模擬的數字不能沿用。

程序：手動模式固定 surge，走一段已知距離，計時。每個值重複 3 次取平均。

| surge | 距離 | t1 | t2 | t3 | 平均速度 |
|---|---|---|---|---|---|
| 10 | 5 m | | | | |
| 15 | 5 m | | | | |
| 20 | 5 m | | | | |
| 25 | 5 m | | | | |

⚠ 同時記錄**起步段**與**巡航段**的差異 —— 模擬裡兩者差了近 2 倍
（0.27 vs 0.5 m/s），盲走時長的計算必須把加速段算進去。

⚠ 順帶記錄當時電池電壓，並在測試日結束前用低電量重測一次 surge=25。
若速度差異顯著，所有以時間為單位的盲走都需要對應的餘裕。

### 4.3 橫桿露出水面的專項觀察

這是本次下水最核心的問題，值得單獨花時間：

- ☐ 實測橫桿露出水面的高度：______ cm
- ☐ 從距離 8 / 5 / 3 m 各拍一張**前相機原始畫面**，人眼判斷橫桿是否可辨
- ☐ 記錄水面倒影是否讓橫桿看起來像兩根
- ☐ 記錄 Snell 窗（畫面上緣的鏡面反射帶）大約佔畫面高度幾成
- ☐ 對比深度 0.2 m 與 0.8 m 時，上述現象的差異

## 5. 事後處理

### 5.1 切段

用 `/orca/test/marker` 把 bag 切成一格一段。每段輸出：

| 欄位 | 來源 |
|---|---|
| 設定（距離／深度／角度／光照） | marker 字串 |
| 總幀數 | `/orca/record/front/compressed` 計數 |
| 有 `gate` 的幀數 | `/orca/perception_array` 含 label=gate |
| `gate` 通過 `is_stable` 的幀數 | 同上，且 `is_stable == true` |
| 平均信心 | 同上 |
| 標籤組成 | 該段所有 label 的次數統計 |

### 5.2 產出兩張表

**格式直接沿用** `GATE_DETECTION_RANGE_FINDINGS.md` 的 §3.2 與 §4，
這樣真實與模擬可以逐格對照：

- **表 A**：距門 × 幀數 × 有 gate% × is_stable% × 平均信心
- **表 B**：距門 × 標籤組成 × ≥1 細長框% × ≥2 細長框%

表 B 決定柱子配對那條路在真實場地值不值得啟用
（模擬中因立柱是灰白色而不觸發，真實場地若柱子是橘紅色，結論可能相反）。

### 5.3 要回答的三個問題

1. **真實場地的偵測斷崖落在幾公尺？**
   → 決定 `ApproachTarget` 的 `distance` 該設多少（模擬版建議 5.0）
2. **下潛到 0.8 m 有沒有把斷崖往前推？**
   → 決定 `SetDepth` 該設多少
3. **柱子配對在真實場地有沒有訊號？**
   → 決定要不要把 `AcquireGateByPostPair` 加回資格賽的樹

## 6. 現場紀律（模擬版 §5 的教訓，換成真實水域的版本）

| 陷阱 | 徵兆 | 對策 |
|---|---|---|
| 不要跟深度控制器對抗 | 實際深度偏離設定 0.4 m 以上 | 站樁期間維持 `manual`，靠人或繩固定 |
| 相鄰距離結果矛盾 | 5.5 m 量到 0%、5.0 m 量到 85% | 量測被污染了。查深度是否在取樣中途改變 |
| 數字完全一致 | 不同距離量到相同信心與框尺寸 | 讀到的是凍結畫面。檢查影像管線是否還活著 |
| 錄了但沒資料 | bag 有 topic 但訊息數 0 | `RECORD_IMAGES` 只傳給了一個堆疊 |
| 現場改參數 | —— | **不要在現場調演算法。** 現場只採資料，分析與調整回實驗室做 |

## 7. 測試日驗收標準

這趟下水**成功**的定義（不是「跑完任務」）：

- ☐ 第 3.1 節主矩陣的粗體格（4.5 / 3.5 / 2.5 / 1.5 m）**至少在深度 0.2 m 全部有資料**
- ☐ 4.1 的 yaw 漂移測試有明確結論
- ☐ 4.2 至少有 surge=25 的速度數字
- ☐ 4.3 的原始畫面已拍到
- ☐ 所有 bag 已備份到至少兩個地方

**未達成也沒關係的**：自主任務跑通、過門成功。
那是下一趟的目標，不是這一趟的。
